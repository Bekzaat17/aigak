# Правила разработки Aigak

Требование владельца проекта: **строго соблюдать SOLID** во всех изменениях.

- **S**: одна причина изменения у класса, функции сценария или React-компонента. HTTP разбирает транспорт и формирует ответ; прикладные сценарии выполняют бизнес-операции; адаптеры работают с внешними ресурсами. Не размещать их в одном обработчике.
- **O**: новые проверки, стратегии, форматы извлечения и провайдеры подключать через существующие контракты и регистрацию в composition root. Не добавлять ветвления по конкретным реализациям в оркестраторы.
- **L**: любая реализация обязана сохранять контракт: семантику ошибок, отмену, точность цитат, ограничения доступа и целостность материалов. Заменяемость подтверждать поведенческими тестами.
- **I**: принимать только необходимые методы зависимостей. Использовать отдельные порты или `Pick<Port, ...>`, не передавать весь контейнер зависимостей каждому классу.
- **D**: прикладной слой зависит от портов, а не от Express, SQLite, файловой системы, браузера или SDK провайдера. Конкретные реализации соединять в `server/bootstrap` и фабриках модулей.

## Структура и стиль

- **DRY**: общие бизнес-инварианты и транспортную сериализацию реализовывать в одном месте; не объединять разные правила только из-за внешнего сходства кода.
- **KISS**: выбирать минимальную архитектуру, достаточную для подтверждённых требований. Не добавлять сервисы, классы и уровни косвенности без отдельной ответственности.

- Один класс на файл, имя файла совпадает с именем класса. Одна React-компонента на файл; состояние и побочные эффекты — в hooks, HTTP-клиент — в `src/api`.
- Промпты находятся только в `server/ai/prompts`. Изменение содержания требует обновления версии промпта и соответствующих тестов.
- Не создавать классы ради формальности: чистые преобразования и отдельные команды могут оставаться функциями.
- Не добавлять универсальные `utils`, service locator, глобальный изменяемый контейнер или зависимости из `shared` на сервер и UI.
- Совместимые re-export файлы существуют для старых импортов; новую реализацию в них не добавлять.
- TypeScript strict, без `any`. ESLint и Prettier обязательны; не отключать правила вместо исправления причин.
- Не менять API, формат сохранённых дел и семантику анализа в рамках рефакторинга без отдельного обоснования и тестов.
- Не менять `data/`, не отправлять реальные материалы внешним сервисам для проверки рефакторинга.

## Проверка

Перед завершением изменений: `npm run check` (форматирование, ESLint, архитектурные границы, тесты, TypeScript и production-сборка).
Для изменения архитектуры добавлять поведенческие тесты заменяемости зависимостей. Успешный линтер сам по себе не доказывает соблюдение SOLID — дополнительно проверять ответственность и направление зависимостей.
