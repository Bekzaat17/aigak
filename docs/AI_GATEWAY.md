# Продвинутый анализ и AI Gateway

## Этапы

Basic: rules → integrity, ни одного запроса модели.
Advanced: rules → context → mechanics → verification → integrity.
Pro добавляет технические связи, legal и pro_review. Legal использует отдельную схему: нормы из сохранённого официального источника, точные цитаты и ссылки на находки. Без корпуса этап пропускается. Маршруты legal/pro_review необязательны в конфигурации и по умолчанию наследуют verification.

1. Context — тип материала, альтернативные объяснения, рекламные цитаты в новостях.
2. Mechanics — ставки, случайность, призы, деньги, бонусы, связь условий.
3. Verification — сверка находок с оригиналами, противоречия, финальный набор.

Каждый этап возвращает assessment, findings, review (статус, неопределённости,
вопросы инспектору и цитируемые противоречия). Код проверяет все цитаты.
Вопросы сохраняются в followUps. Инспектор отвечает, привязывает источники и запускает новую версию. Ответы передаются отдельно от первичных материалов как непроверенные заявления; точные цитаты по-прежнему проверяются только по источникам. Существующая проверка инспектором остаётся доступна.

Итоговые находки заменяет только Verification. Базовые и промежуточные наблюдения
сохраняются в stages. При сбое сохраняются предыдущие результаты, весь запуск становится
partial, процент скрывается. Для ambiguous/insufficient процент тоже не показывается.

## Границы модулей

Стратегия → AdvancedCheck → GatewayAnalyzer → AiGateway → ModelAdapter → провайдер.

- contracts.ts — общий интерфейс модели без логики азартных игр.
- config.ts — проверка серверной конфигурации.
- adapters.ts — HTTP-протоколы, отказ модели, завершённость ответа, usage.
- gateway.ts — маршрутизация и выполнение; принимает валидатор результата.
- prompts.ts — версионированные инструкции пяти задач.
- schema.ts — строгий ответ и проверка цитат по переданным материалам.
- inspection/provider.ts — адаптер предметной области к универсальному шлюзу.
- shared/inspection-presentation.ts — представление журнала для документов.

Материалы и предыдущие выводы передаются в user input, не добавляются к системным
инструкциям. Агентам не выдаются инструменты браузера или выполнения команд.
Сервис пакета по-прежнему получает данные и ничего не знает о провайдере ИИ.

## Настройка

Без нового файла сохраняется поддержка OPENAI_API_KEY / OPENAI_MODEL, по умолчанию
OpenAI Responses. Тестовая модель по умолчанию — `gpt-6-luna`, reasoning effort `low`,
без автоматических повторов или переключения на дорогую модель. Качество на материалах
проекта ещё требует реального eval. В `.env` можно задать:

    OPENAI_MODEL=gpt-6-luna
    OPENAI_REASONING_EFFORT=low

Если задан только OPENAI_MODEL, effort не отправляется: это сохраняет совместимость
с моделями без reasoning. Для явных JSON-профилей используется `reasoningEffort`.
Допустимые значения effort зависят от модели; несовместимое значение даёт явную ошибку.
AIGAK_AI_CONFIG имеет приоритет над OPENAI_MODEL / OPENAI_REASONING_EFFORT.

Для явных профилей задать в .env:

    AIGAK_AI_CONFIG=./config/ai.example.json
    OPENAI_API_KEY=...
    LITELLM_API_KEY=...

В config/ai.example.json два профиля: default (Responses) и gateway (Chat Completions).
Второй профиль сам по себе НЕ используется: маршруты ссылаются только на default.
Для LiteLLM Proxy назначить маршрут verification: ["gateway"].
Для резерва после временной ошибки: verification: ["default", "gateway"].

Можно назначать разные model или snapshot ID каждому профилю. model у LiteLLM может
быть настроенным на прокси псевдонимом. Ключи берутся из переменных окружения по apiKeyEnv;
в JSON их нет. Изменения требуют перезапуска API и воркера (`./scripts/up.sh` для Docker). Конфигурация не принимается от клиента.

Новый провайдер: реализовать ModelAdapter.complete, зарегистрировать в createAiAnalyzer
и расширить разрешённые идентификаторы в схеме конфигурации.
Новые инструкции/схемы требуют повышения PROMPT_VERSION / SCHEMA_VERSION и проверки eval.
Переключение профилей не требует изменений проверок и сборщика пакета.

LiteLLM не установлен и не запущен приложением: реализован HTTP-адаптер к отдельно
настроенному прокси. Выбранная модель и прокси должны поддерживать JSON Schema.
Неподдерживаемые параметры приводят к явной ошибке без ослабления проверки.
temperature опциональна: не задаётся по умолчанию, так как доступна не у всех моделей.

## Экономия без изменения доказательств

- OCR, извлечение текста, базовые правила и проверка точных цитат выполняются локально.
- `inspection/compact-sources.ts` перед отправкой заменяет полностью одинаковые длинные
  тексты ссылкой `textRef` на первый текст. ID и URL каждого источника сохраняются;
  совпадение текста не считается независимым подтверждением. Короткие повторы оставляются,
  если ссылка длиннее текста. Сохранённые материалы не изменяются.
- Пробелы, цитаты, отрицания и отличающиеся фрагменты сохраняются точно. Нет обрезания,
  удаления «неважных» абзацев или автоматического пропуска AI из-за отсутствия ключевых слов.
- Пустой блок заявлений инспектора не передаётся. Промпт просит краткие объяснения,
  сохраняя неопределённость и доказательства.
- `reasoningEffort: low` ограничивает усилие рассуждения; `maxOutputTokens` ограничивает
  ответ вместе с reasoning-токенами. Неполный ответ считается ошибкой, а не готовым анализом.
- Лимит входа проверяется после упаковки. Процент экономии зависит от количества дублей;
  уменьшение символов не равняется точному уменьшению токенов.
- Не используется общий кеш ответов между делами: разные источники, ответы инспектора
  и версии анализа должны проходить собственную проверку.

## Ограничения и журнал

- Три логических AI-этапа. На профиль максимум один повтор, в маршруте до двух профилей.
  Общий предел — 12 сетевых попыток. По умолчанию три попытки.
- По умолчанию таймаут попытки 45 секунд, срок анализа Advanced 210 секунд, Pro 330 секунд; сбор источников имеет отдельные лимиты.
- Повторяются сетевые ошибки, таймауты, 429 и 5xx. 401/400, отказ модели,
  неполный ответ, ошибка схемы или цитаты завершают этап без fallback.
- Родительская отмена прекращает повторы и переключения.
- Максимум 180 000 символов сериализованного входа вместе с предыдущими наблюдениями.
  При превышении — AI_INPUT_TOO_LARGE, без молчаливого обрезания.
- В stage.aiAttempts: профиль, адаптер, запрошенная модель, reported actualModel,
  версии, время, статус, токены (если переданы). Нет ключей и сырых ответов ошибок.
  Если прокси не сообщает реальную модель, actualModel неизвестна; запрошенный alias
  нельзя считать подтверждением конкретной модели.
- aiCalls — логические этапы, aiAttempts — реальные попытки.
  Денежная стоимость не вычисляется: тарифы провайдеров не зафиксированы.

## Показатели в интерфейсе

В карточке результата показывается блок «Время и расход анализа»: весь цикл текущего
запуска (включая очередь и сбор), время проверки материалов, число запросов, входящие,
выходящие и суммарные токены. При повторном анализе начало берётся из revision.started,
а не из даты создания дела. В раскрываемых технических деталях указаны время и расход
каждого этапа, а также отдельные попытки с моделью и длительностью.

Суммы включают известный расход неудачных попыток и повторов. Если usage отсутствует,
отображается «нет данных» или нижняя граница ≥, а не фиктивный ноль. Прерванный запрос
может быть оплачен провайдером, но не попасть в сохранённую статистику. Это показатели
текущего запуска, а не платёжный счёт и не сумма по всем версиям дела.

## Проверки качества

npm test проверяет маршрутизацию, границы Basic, три этапа, цитаты,
fallback, отмену, протоколы адаптеров и лимиты на подставных ответах.

Для реального прогона после настройки ключей:

    npm run eval:ai -- --live --case=ru-offer

Это один синтетический пример и три логических AI-этапа. Для всех примеров:

    npm run eval:ai -- --live

Это шесть синтетических RU/KK примеров и 18 логических этапов (с повторами запросов больше).
Команда отправляет примеры настроенным провайдерам и расходует API-бюджет.
Она печатает результаты, inputTokens/outputTokens и число попыток без usage
(missingUsageAttempts — отсутствие данных не означает нулевую стоимость), а также ненулевой exit code при несовпадении ожидаемых статусов.
Этот маленький набор — smoke test, не измерение точности на реальных делах.
