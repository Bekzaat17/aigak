# Сбор и подтверждение страниц

MVP запускает новые проверки по ссылке. Старые дела и API импорта материалов сохранены для совместимости.

В `server/bootstrap/create-url-collector.ts` регистрируются независимые способы сбора:

- HTTP-оригинал и извлечение HTML.
- Chromium с исполнением JavaScript и ожиданием читаемого содержимого.
- Мобильный размер экрана и OCR снимков при недостаточном результате браузерного сбора.

Ошибка HTTP не останавливает браузер. `UrlCollectionService` зависит от контракта `UrlCollectionMethod`, сохраняет длительность, материалы и качество каждой попытки. Оценка объёма текста — проверка пригодности, а не утверждение о полноте всего сайта. Ограниченный сбор не считается отсутствием признаков.

Браузер использует проверку публичных адресов и закрепление DNS каждого HTTP-соединения. Сохраняются ограничения GET, загрузок и WebSocket. Бюджет — 600 запросов, 100 MiB, 90 секунд на контекст, 12 одновременных запросов; браузерные заголовки передаются по разрешённому списку без cookie и Authorization. В публичном режиме POST и вход в аккаунт не выполняются. Настроенный вход Pro описан ниже; ставки, обход CAPTCHA и платежи не выполняются. Некоторые сайты могут оставаться недоступными; результат обязан это показывать.

После анализа `FindingVerificationStage` проверяет точную цитату в сохранённом тексте и повторно открытой странице. `BrowserFindingVerifier` прокручивает нужный блок, проверяет видимость и отсутствие перекрытия, сохраняет неизменённый кадр участка, повторно сверяет цитату и положение. Привязка содержит источник, цитату, снимок и время. Это проверка видимого DOM до и после снимка, а не независимая экспертная проверка изображения. Изменившаяся, скрытая или отсутствующая цитата не получает визуального подтверждения. Старые неподтверждённые общие скриншоты не подставляются в находку.

`refreshSources: true` в запросе повторного анализа создаёт ревизию и обновляет сбор. Оригиналы и предыдущий результат сохраняются; устаревшие снимки исключаются из текущего AI-входа. Новые поля коллекции и визуального подтверждения необязательны для старых дел.

Оценка содержимого отделена от юридической применимости. При завершённых содержательных этапах результат `not_found` и процент ИИ сохраняются даже при пробеле в правовых источниках. Неудача содержательного этапа или недостаточный сбор убирают процент. Процент не откалиброван и не является вероятностью незаконности.

Проверки: `npm run check`, `node --import tsx --test tests/browser-collection.integration.ts`, `node scripts/smoke-ui.mjs`. Браузерные тесты используют Chrome (`BROWSER_CHANNEL`) и синтетические страницы; тесты не требуют передачи материалов AI-провайдеру.

## Pro: настроенные сценарии входа

Реализован выбор публичного анализа, входа или регистрации по подготовленному
профилю. Профили задаются администратором через `AIGAK_AUTH_PROFILES` (JSON-массив).
Инспектор выбирает профиль и сценарий; API отдаёт только название, домен и доступность
регистрации. Пароли остаются на сервере. Профиль содержит `id`, `name`, `origin`,
`registration`, `login`, необязательный `register`, `successSelector` и `readUrls`.
Форма содержит `url`, `fields` (селектор → значение), `submitSelector`, `submitUrls`.
Все страницы и разрешённые POST должны принадлежать указанному HTTPS origin.

Вход считается успешным только при появлении настроенного видимого признака сессии.
До четырёх внутренних страниц проверяются повторно. Материалы помечаются «после входа»;
контекст сохраняется до проверки цитат и закрывается в конце обработки.
Повторная регистрация в том же деле блокируется, в том числе после перезапуска.
POST разрешён только во время входа и только на перечисленные адреса (до 8 запросов).

Необязательный `verification` содержит `endpoint`, `token`, `allowedPathPrefix`.
Доверенный почтовый адаптер возвращает JSON `{ "verificationUrl": "https://…" }`;
ссылка проверяется по домену и пути. Тестовая регистрация проверена на синтетическом
сайте с почтовой заглушкой. Создание настоящего почтового ящика не подключено.
CAPTCHA/2FA и неподдерживаемая форма завершаются ограничением; возобновление с участием
человека пока не реализовано. Это настроенный исполнитель, а не универсальный AI-агент.

В Pro общий бюджет сбора — 300 секунд; затем выполняются анализ и проверка находок,
поэтому это пока не предел полного времени проверки. Дополнительный native Chromium
использует собственный TLS через DNS-проверяющий CONNECT-прокси: это независимая от
Node HTTP стратегия. Она не меняет внешний IP и не гарантирует доступ при сетевой блокировке.

## Целевой сценарий автономного агента

Требование владельца: инспектор выбирает сайт и разрешённый сценарий, остальное
выполняет агент с проверками и запасными стратегиями.

Проверены готовые библиотеки:

- [Stagehand](https://github.com/browserbase/stagehand) — основной кандидат для
  семантического поиска элементов и восстановления действий при изменении формы.
  Для TypeScript проекта подходит лучше отдельного Python-процесса.
- [Browser Use](https://docs.browser-use.com/) — альтернативный браузерный агент.
- [Crawlee](https://crawlee.dev/js/api/3.15/playwright-crawler/interface/AdaptivePlaywrightCrawlerOptions)
  — повторные попытки, переключение HTTP/браузер, resultChecker и resultComparator.

Библиотеки пока не подключены. Установка SDK сама по себе не заменяет критерии
достоверности и не устраняет сетевые блокировки.

Следующая реализация:

1. Сценарий определяет разрешённые домены, действия, критерии успеха и общий бюджет
   400 секунд, включая анализ и финальную проверку. Регистрация и вход идут в одной
   сессии без параллельной отправки форм.
2. Публичные независимые стратегии можно выполнять параллельно с отдельными
   результатами. Неудача запускает следующую применимую стратегию; одинаковая ошибка
   не повторяется бесконечно. Частичный результат сохраняется при исчерпании бюджета.
3. Stagehand через узкий порт предлагает элементы/действия. Исполнитель проверяет
   разрешённость перед действием; секреты подставляет вне модели. После каждого шага
   проверяется фактическое состояние страницы, а не только ответ агента.
4. Почтовый провайдер создаёт выделенный ящик и получает подтверждение; сообщения,
   коды и токены не попадают в модель и отчёт. Нужен подключённый провайдер.
5. Сверка результатов: один факт объединяет совпадающие источники; противоречия
   сохраняются отдельно. Снимок проверяет точную находку. Закрытые страницы не
   представляются публичной рекламой, а ошибка доступа — отсутствием признака.
6. Краткий отчёт содержит выводы, причины, ссылки и доказательства. История включает
   каждую попытку, причину перехода, длительность, фактические токены и расходы.

Критерии приёмки: изменённая форма, неверный пароль, письмо с неверным доменом,
истечение сессии, CAPTCHA/2FA, отмена, исчерпание бюджета, падение отдельного сборщика,
расхождение источников, отсутствие секретов в сохранённых артефактах и экспорт истории.
